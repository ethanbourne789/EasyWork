已产出两类签名 APK：`android-release/EasyWork-universal-release-signed.apk`（~32MB，4 ABI，⚠️ 仍为 4KB 对齐旧包）与 `android-release/EasyWork-arm64-release-signed.apk`（~10.4MB，arm64 单架构，**16KB 页对齐已达标**），均用 `E:\Pub\AndroidKey\release-key.jks`（alias easywork）签名，apksigner v2+v3 通过。详细踩坑与脚本见 skill `tauri-android-build-windows`。

关键结论（与 skill 互补）：
- **架构**：`tauri android build --apk -t aarch64`（`-t` 可选 `aarch64/armv7/i686/x86_64`）单架构 ~6 分钟；universal 4 架构 ~20 分钟。`bundle.android` 无 `abi` 字段，别乱配。
- **图标（✅ 构建期，已验证）**：Tauri 读 `src-tauri/icons/android/`（不是项目根 `icons/android/`）。把库图标复制到 `src-tauri/icons/android/` 后 `tauri android build` 即生成正确自适应图标（foreground+background+adaptive XML，已核对 `res/mipmap-xxxhdpi/ic_launcher_foreground.png` 哈希与库里 `ca09ebc5…` 一致）。**不要再走 APK 后处理植入图标**（旧 `repackage_apk_icons.py` 方式脆弱且会破坏对齐）。AAPT2 会把资源名混淆成 `res/-1.xml`/`res/-B.png` 等短名（映射在 resources.arsc），属正常，不代表图标丢失。⚠️ 启动器可能缓存旧图标：重装后若仍显示旧图标，重启手机或清启动器缓存（设置→应用→[启动器]→存储→清除缓存）。
- **✅ 16KB 页对齐修复（已验证，这是 16KB 机型「打开即退出」的根因）**：Tauri 的 `android-studio-script` 用自有 `CARGO_TARGET_*_RUSTFLAGS` 覆盖 max-page-size，故 env 注入无效。改绕过 Tauri 直接 `cargo build`：写 `scripts/arm64-link-wrap.cmd`（NDK clang + `-Wl,-z,max-page-size=16384`），设 `CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER` 指向它后 `cargo build --target aarch64-linux-android --release`（全量重编 ~4.5min），`.so` LOAD 段 `Align` 变为 `0x4000`。再把该 `.so` 换进 unsigned APK → 重打包（`.so`/`resources.arsc`/`AndroidManifest.xml` 用 ZIP_STORED）→ `zipalign -f -P 16 4`（注意 `-P 16` 不是 `-p 4`，`-p` 只做 4KB）→ `apksigner sign`。`zipalign -c -P 16 4` 退出 0 即达标。16KB 对齐在 4KB 设备也能加载，无副作用，应作为默认产出。
- **不能直接 `./gradlew assembleRelease` 重打包**：`rustBuildArm64Release` 任务要连 `tauri android build` 父进程的 WebSocket 读参数，直跑无 WS 报 `ConnectionRefused 10061`；改走「APK 后处理换 .so」路线（见上）。
- **崩溃排查结论**：若换上 16KB 包仍「打开即退出」，则不是打包对齐问题而是运行时错误——需用设备 `adb logcat -b crash -d` 抓崩溃栈定位（本机无连接设备/无 AVD，无法自测）。

## 邮件同步架构收敛：单一收信器 fetch-mail + 删除云端 mail-sync（08-11 上午）
用户质疑「为何全量拉取」，经核查发现比预想更严重的架构债务，已全面统筹修复（用户授权删云端文件）。

**根因**：线上 `mail-sync`(v15) 实际是**坏的**——它 upsert 的列（`uid_validity/uid_next/total_count/synced_at/kind`）与 `emails.folder` 在云端真实表结构里都不存在（云端 `email_folders` 仅 name/imap_path/unread_count/sort_order；`emails` 唯一约束是 `(email_account_id,message_id)`，无 `folder` 列），每次调用必报错，`email_folders` 从未被正确填充。真正在跑且**已实现增量**的是 `fetch-mail`（用 `email_accounts.last_synced_uid` 游标 + 首次窗口 + 附件），由 `pg_cron`(0019) 每 5 分钟调用、UI `useSyncMail` 也直接调它。`mail-sync` 既没被 UI 调、也没被 cron 调，是冗余失效的遗留，且用 bespoke 手写 `imap.ts` 双栈（与 fetch-mail/send-mail/manage-folder 的 imapflow `_shared/mail.ts` 并存）。

**决策**：架构收敛为单一收信器 `fetch-mail`，吸收 mail-sync 的「发现文件夹 + 全文件夹同步 + 文件夹元数据」，然后删除云端 `mail-sync`（含孤儿 `imap.ts`）。

**增量模型（按用户要求）**：每文件夹用 `email_folders.last_uid` 游标；首次同步 / `uid_validity` 变更（文件夹被服务端重建）→ 仅拉最近 WINDOW=200 封（限定数量）；之后 → `UID ${last_uid+1}:*`（真增量）。带 HARD_CAP=1000 防游标异常落后时单次拉取过大。删除对账：`client.search({uid:'${fromUid}:*'})` 比对远端仍存在的 UID，清理本地已被删邮件（仅限本区间）。旗标 `flags`→`is_read/is_starred`。附件走 `uploadAttachment`。INBOX 游标同时写回 `email_accounts.last_synced_uid`（兼容旧字段）。保持 UI/cron 调用契约不变。

**云端 schema**：`email_folders` 增加 `last_uid bigint` / `uid_validity bigint` / `total_count int not null default 0` / `synced_at timestamptz`（用 `execute_sql` 直接改云端，因本地迁移已滞后；补本地迁移 `0023_email_folder_sync_cursor.sql` 备案，IF NOT EXISTS 幂等）。

**`_shared/mail.ts`**：抽出导出 `parseMessageSource(source, uid)`（原本 `fetchNewMessages` 内联的 PostalMime 解析），供全文件夹同步复用；`fetchNewMessages` 改为调用它。

**部署验证**：`supabase functions deploy fetch-mail --no-verify-jwt` → v8 ACTIVE、含增量逻辑、打包 `_shared/mail.ts`（带 `parseMessageSource`），bespoke `imap.ts` 随之消失。`supabase functions delete mail-sync` → 已删除。现云端函数 4 个：mail-account / fetch-mail / send-mail / manage-folder。

**🔴 重要长期事实：本地仓库已滞后于云端 Supabase**。证据：(1) 云端 `email_folders` 比本地迁移 0005 多若干列（且旧 mail-sync 写的列本地根本没有）；(2) `mail-sync`/`mail-account` 的源码**不在本地仓库**（仅云端有）。今后改 Edge Function 或写 SQL **必须先 `execute_sql` 查 information_schema 核对云端真实表结构**，不能只信本地 `supabase/migrations/`。任何「源码」改动都要 `functions deploy` 才上线（沿用 08-11 教训）。

**`mail-account`**（云端 v4，verify_jwt:true，自包含单文件）：负责邮箱账户绑定/删除（加密 auth_code→enc_password 存 `email_accounts`，providers 仅 qq/qiye163）。它不是 IMAP 同步函数，保留。注意其密码列名是 `password`（存加密串），`fetch-mail`/`_shared/mail.ts` 读 `account.password` 一致。
